# LLM Wiki — a Lightning Lesson

Turn a pile of articles into a **cited, browsable knowledge base that an LLM builds and maintains**.

This repo is a worked example: six articles about building a *semantic layer for GenAI* go in as raw
text, and come out as a structured [Open Knowledge Format](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)
(OKF) bundle of sources, entities, concepts, relationships and an overview — every claim footnoted
back to the article it came from.

---

## The idea (Karpathy's split)

The "immutable raw sources vs. LLM-compiled knowledge" framing follows
[Andrej Karpathy's note](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).

```
   raw/  ──────────────▶  the LLM reads & compiles  ──────────────▶  wiki/
  (immutable sources)         (judgment: what's a fact,            (an OKF bundle: one
   never edited                 which entities, how they relate)     concept per file, cited)
```

- **`raw/`** is the ground truth: the original articles, never edited.
- **`wiki/`** is *compiled* knowledge — the LLM is the compiler. Pages are Markdown with YAML
  frontmatter; every claim ends in a `[^source]` footnote so you can always trace it back.
- The wiki is **stateless**: the Markdown pages *are* the source of truth. No database, no hidden
  index — point any OKF tool (or Obsidian) at `wiki/` and it works.

## File-name safety (Windows / git)

Source titles often contain characters like `?` or `:` that are **illegal in file names on
Windows** — a repo containing them can't be checked out there. `check-filenames.sh` flags
any tracked (or staged) path that is unsafe to commit: illegal characters (`< > : " / \ | ? *`),
trailing spaces or dots, control characters, and reserved device names (`CON`, `NUL`, `COM1`, …).

```bash
./check-filenames.sh          # check staged files (what a commit would add)
./check-filenames.sh --all    # check every tracked file
```

To run it automatically before every commit, enable the shared hook **once per clone**:

```bash
git config core.hooksPath .githooks
```

(`core.hooksPath` is local config, so each clone opts in; the hook itself is version-controlled.)

## Two ways to build it

Both produce the *same* `wiki/` bundle; both have the LLM write the pages. They differ only in who
drives.

| | **`llm-wiki`** (scripted) | **`llm-wiki-lite`** (hand) |
|---|---|---|
| Driver | `wiki.py` CLI orchestrates the model | you ask the agent; it writes pages directly |
| Setup | Python + uv + an API key | none — just the agent |
| Extras | `lint`, `index`, `query` commands | self-check by hand |
| Best for | hundreds of sources, automation | a small corpus, zero setup |

Each skill lives under `.agents/skills/<name>/` with its own `SKILL.md` and step-by-step `README.md`.

## How a build works

1. **Ingest, oldest first.** For each source the LLM writes a summary page in `wiki/sources/`.
2. **Promote on evidence.** An entity or concept gets its own page once it's mentioned **3+ times**
   across the wiki; below that it stays a *candidate* listed in `index.md`.
3. **Relate.** When a source makes an explicit claim about how two things relate, a relationship
   page is written (e.g. *semantics vs ontology*, *semantido builds on SQLAlchemy*).
4. **Synthesize.** An overview page ties the big picture together.
5. **Index, log, lint.** `index.md` is regenerated by scanning the pages; `lint` checks that every
   link resolves, every claim is cited, and nothing is orphaned.

Then you can **ask the wiki questions** and get answers cited to specific pages.

## Setting your API key

Copy the example env file, drop in your key, and you're set — `.env` is gitignored so your key is
never committed:

```bash
cp .env.example .env            # then edit .env and paste your ANTHROPIC_API_KEY
```

**Prefer OpenAI?** The scripted pipeline is provider-agnostic — run `uv sync --extra openai`, then
set `LLM_PROVIDER=openai`, `OPENAI_API_KEY` and `LLM_MODEL` in `.env` (see the comments in
`.env.example`). The DCI notebook stays Anthropic-only.

To launch Claude Code with that key loaded, use the helper script (it sources `.env`, exports the
key, then starts `claude`; extra args pass through):

```bash
./start-claude.sh               # or: ./start-claude.sh --model opus
```

## Quickstart (scripted skill, with uv)

```bash
uv sync                                   # create .venv with the anthropic SDK
cp .env.example .env                       # set ANTHROPIC_API_KEY  (OpenAI: uv sync --extra openai)
set -a && source .env && set +a            # load the key into this shell

# run the pipeline (commands live in the skill; run from the repo root)
uv run python .agents/skills/llm-wiki/scripts/wiki.py ingest      # compile raw/ → wiki/
uv run python .agents/skills/llm-wiki/scripts/wiki.py lint        # audit the bundle (no key needed)
uv run python .agents/skills/llm-wiki/scripts/wiki.py query "what do my sources say about text2sql?"
```

`lint` and `index` need no API key. To use the **lite** skill instead, don't run anything — just ask
the agent: *"ingest the files in `raw/` using the llm-wiki-lite skill."*

## Why this matters (talking points)

- **Provenance over vibes.** Every fact is footnoted to a source; the wiki can be audited and a
  withdrawn article's claims can be pruned back out.
- **The LLM does judgment; the tooling does bookkeeping.** Entity resolution, "is this a claim?",
  prose — model. Discovery, mention-counting, index, lint — code.
- **Drift is the enemy.** The example corpus is itself *about* keeping meaning from drifting away
  from data; the wiki applies the same discipline to the articles.
- **Stateless on purpose.** Dropping a central state file keeps the knowledge base in plain,
  diffable Markdown that scales to hundreds of documents and reads fine on its own.
